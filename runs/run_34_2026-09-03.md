# Run 34 — 2026-09-03

## Scope
Fresh literature review and a focused audit of the executable validation path. Emphasis: cost-aware model selection, execution realism, and preventing invalid artifacts from reaching performance metrics.

## Meaningful findings

1. A 2026 BTC walk-forward study using roughly 70,000 hourly observations and 27 folds reports a large disconnect between predictive accuracy and net trading performance: naive sign-based strategies fail under 10 bps transaction costs, while forecast-magnitude filtering can reduce turnover and recover profitability in selected configurations. The authors do not establish formal statistical dominance of XGBoost over neural alternatives. This is directly relevant to our cost-aware execution hypothesis, but it is external evidence, not evidence for our model.

2. A July 2026 study of hourly Bitcoin ML trading likewise reports that explicit fees, bid-ask spreads, and slippage can erase apparent gains from increasingly complex predictors, while transaction-cost-aware filtering can be more important than marginal architecture improvements. The result is consistent with treating execution as part of the model rather than as an afterthought.

3. The current production validator now records duplicate timestamps before mutation, but `validate_predictions()` still proceeds to `drop_duplicates()` after setting `validation_error`. That means a malformed artifact can still generate downstream metrics. This is the clearest executable integrity defect available from the repository snapshot and should be fixed before numerical promotion.

4. The current cost stress adapter is wired to the scalar fee/slippage interface, removing the earlier stale-config API mismatch. However, the execution model still needs independent spread and market-impact components before capacity claims can be made.

## New hypotheses

### H31 — No-metric-on-invalid-artifact
If a prediction artifact violates uniqueness of decision timestamps, validation must terminate before classification, equity, or trade metrics are calculated. The expected test is a duplicate-row fixture whose output contains an error and no performance metrics.

### H32 — Cost-aware signal threshold
For a frozen prediction stream, an execution threshold based on expected edge minus total round-trip cost should reduce low-edge turnover without materially degrading high-confidence trade expectancy. Thresholds must be frozen before the final holdout.

### H33 — Independent execution-cost elasticity
Net performance should be evaluated over independent commission, half-spread, adverse-slippage, and market-impact grids. A candidate that survives only a combined single-point assumption is not robust evidence.

### H34 — Search-adjusted family superiority
After the complete trial registry is frozen, the best candidate must clear family-level SPA/Reality Check in addition to CPCV/PBO and DSR. An individual significant Sharpe is insufficient after model/feature/threshold search.

## Required next executable work

1. Change duplicate handling to fail immediately before any metric calculation.
2. Add an explicit execution-cost object or equivalent interface with commission, half-spread, adverse slippage, and impact recorded per trade.
3. Add a trial registry and immutable prediction manifest (data hash, feature version, model config, threshold, split/embargo rule, execution config).
4. Generate frozen OOS predictions and run the predeclared cost/turnover grid.
5. Apply CPCV/PBO, DSR, and SPA/Reality Check to the complete candidate family, then evaluate the untouched holdout once.

## Evidence status

No new project profitability claim is promoted. The robust finding is methodological: transaction costs and execution filtering deserve first-class treatment, while the current validator still permits metrics to be computed after a data-integrity violation. Until the fail-closed fix and immutable OOS artifacts exist, additional backtest numbers would not meet the project's evidence standard.
